# Bricks: concrete sparks for Agent evolution

An Agent can understand a principle yet have no idea what to try next. These **bricks** are concrete starting moves, not a doctrine, a checklist, or a quota. Pick, change, combine, invert, or discard them according to the real Host and task. A brick is not evidence that the move helps; only observed results can show that.

Use the smallest useful move. Do not create a new job, artifact, review, or tool just to demonstrate a brick. Host authority, explicit user stop, privacy, bounded cost, recovery, and real verification still apply. Nothing in this page automatically enables a hook or grants new access.

## Keep work moving

1. **An Agent asks, “Should I save this?”** If it already has authority and enough context, decide and act now. If the question is non-blocking but merits a fresh perspective, preserve **the question itself** as a possible successor task: when the current round finishes and an authorized next round actually starts, let the later Agent reconsider the earlier question independently. If no continuation mechanism exists, do not claim it will run. A genuinely required human approval stays with the human.
2. **A completed task leaves the next ready task waiting until a timer fires.** Try a completion-event hook that releases the successor as soon as its dependencies are satisfied. Keep polling only as a fallback for events the Host cannot observe.
3. **Three tasks are active and one is forgotten.** Try one existing task ledger that records ownership, readiness, dependency, completion, failure and stop. Resist a second ledger that only duplicates the first.
4. **An Agent reports an error, then treats its report as a fix.** Connect detection to a bounded diagnosis, authorized repair, a real verification check and a clear unresolved outcome when repair fails.
5. **A conversation is getting too long to work reliably.** Test a minimal handoff of the user goal, authority, active state and next action into a fresh session, preserving the original communication channel when the Host supports it. Confirm continuity rather than assuming it.
6. **The user chooses “end this project” over “keep optimizing.”** Stop the project's coding, research, reviews and successor loops immediately. Do not run one last cleanup experiment under the banner of learning.

## Turn questions and disagreement into discoveries

7. **The same trivial question keeps being escalated to the user.** Look for a reusable local decision criterion or a tiny tool that makes future authorized decisions without asking. Keep genuine authority boundaries.
8. **Two Agents review the same task and agree instantly.** Ask one to find a different root cause, a counterexample or a simpler execution path. Compare effects on a later real task; consensus is not proof.
9. **A difficult execution has a long transcript.** Share only an authorized, sanitized, bounded process trace with another Agent; ask where unnecessary work, missed evidence, or a better stopping point appeared. Treat the review as a candidate, not a verdict.
10. **A test passes but users still experience the failure.** Try a small *representative* real case rather than another convenient self-designed fixture.
11. **A solution keeps generating more rules.** Reverse the question: which instruction, memory, gate, role or step can be removed while preserving the actual result?
12. **The suspected bottleneck was just solved.** Look again at the whole task. The decisive constraint may now be latency, human attention, missing capability, or something else; do not keep optimizing yesterday's bottleneck.

## Grow or borrow a useful “organ”

13. **An Agent needs something it cannot do.** Inspect the Host's existing capabilities, registries and nearby reusable tools before inventing a new subsystem. Verify availability, compatibility and permission.
14. **Its current toolbox has become its entire imagination.** As one *example* of looking outward, inspect **GitHub Trending's top 10 projects** for techniques, reusable capabilities or surprising combinations. Then follow adjacent fields, less popular projects, papers, tools or other Agents when useful. “Top 10” is a doorway, **not** a required recurring scan or a popularity-based installation queue.
15. **A workflow pattern in another field looks strangely familiar.** Try transferring its *mechanism* across domains—for example, an event-trigger pattern from a job queue to Agent task continuity—before importing the whole foreign architecture.
16. **An Agent has spare time and wants to grow a new capability.** Let it choose a small, high-leverage skill, tool or connector that fits its real Host; test the candidate reversibly, or choose no growth. Selecting an idea never grants installation or access authority.
17. **A tool works in the foreground but breaks in background execution.** Evaluate the Host as one system: interaction, jobs, memory, tools, handoffs, channels and recovery must combine into an actual user outcome.
18. **Agent A has a useful capability that Agent B lacks.** Try authorized peer discovery, a reusable tool, or a bounded task exchange rather than rebuilding everything. Check what either Agent can *really* execute.

## Evolve the evolution process itself

19. **The Agent's improvement loop spends more than it saves.** Measure one cycle's total time, model/tool burden, user attention and later benefit; simplify or retire its trigger, review or record if net value is negative.
20. **An idle interval appears.** It might support a low-cost review of a recurring failure, a speculative idea or external exploration. It might also be better left empty as reserve for foreground work and recovery. Idle is not a debt to fill.
21. **A promising new skill passes its first test.** Keep the smallest baseline, try a bounded real task, and record whether it truly transfers. Be willing to revise, reject or restore.
22. **A fix passes only after a string of failures and repairs.** Preserve the useful failure → repair → verification evidence, not every verbose thought or log.
23. **The Agent is steadily polishing a 1% gain.** Ask whether changing the tool, interface, collaboration path, or task framing could create a 10x improvement. Try a cheap discriminating check before committing.
24. **A constraint looks purely negative.** Ask whether a low budget, limited access, old hardware or failed attempt reveals a reusable capability or simpler path. Accept the idea only when it creates an observable gain, not a comforting story.

## Discover new abilities beyond inherited examples

25. **The Agent repeats a failure pattern but lacks a way to see it.** Compare a few real executions and invent a small self-observation probe—for example, a check for needless tool calls after sufficient completion. Trial the probe on a real task; retire it if its overhead exceeds the errors it catches.
26. **Another Agent succeeds through a method neither Agent already exposes as a tool.** With permission, study what made its execution different, then experiment with a reusable coordination or verification capability. Do not assume copying its prompt, agreeing with its verdict, or cloning its entire workflow is the new organ.
27. **Existing categories split one user outcome across “chat,” “background,” “memory,” and “tools.”** Question the categories themselves: map the end-to-end outcome and test a simpler boundary or responsibility model. Sometimes the new capability is a better way to see the problem, not another plugin.
28. **An unrelated field reveals a surprising way to solve an Agent problem.** For example, borrow inventory reconciliation to detect user requests lost across sessions, or a feedback controller's correction pattern to avoid blind retries. Extract the smallest transferable mechanism, adapt it to the Host, and verify it in context.
29. **A real task reveals an opportunity no user, guide, or catalog suggested.** Turn the observed situation into an original brick: what happened, what unexpected move might help, and what result would disprove it? Try it when worthwhile and authorized. An Agent can originate new bricks, not just execute inherited ones.

30. **An Agent is immersed in its own execution and cannot see its blind spots.** A repeated retry, surprising time/tool cost, user correction or consequential completion may be a useful trigger. Freeze a small redacted trace and inspect it from an outsider's view; when the Host supports it and the benefit warrants the cost, launch an isolated read-only reviewer subprocess/session, optionally on a different LLM. Use evidence to identify one specific change, decide independently, and verify on later real work. A same-session perspective shift is weaker than independent review; no automatic runner, mandatory review or endless loop is implied. See [the concrete Host wiring example](examples/evolution/OUTSIDER-REVIEW.md).

31. **A mature Agent reads ENA and starts duplicating what already works.** It has a rollback drill, change-management skill, session handoff and memory cleanup, yet begins creating `ENA.yaml`/`SYSTEM.yaml` only because the example does. On its next real upgrade or recovery task, map needed outcomes to *observed* Host behavior and evidence; test one missing ENA idea if useful, but skip duplicate configuration. Compare setup cost and later results. If it deliberately installs ENA's reference tools, their READY gate remains separate. “I have a plugin” is not “I verified it works.”

32. **A small task quietly burns tokens and money—and the same habit keeps returning.** For example, changing two Agents' default model routes repeatedly consumes paid model calls while no configuration check succeeds. Instead of imposing a low turn cap or optimizing for the smallest bill, compare available usage evidence (or an honest rough proxy) with *completed, verified work* across similar tasks. Look for a repeatable habit: rereading the same context, retrying without new evidence, choosing an ill-suited tool/model, failing to recognize completion, or losing progress at handoff. Try one small change to that workflow and check later tasks for **equal or better quality and completion with less total waste** (including retries and repair). Spend more tokens when the task genuinely needs them; a cheap failure or a degraded answer is not efficiency. Do not invent a precise bill when the Host exposes no meter.
33. **“抽刀断水水更流” — cutting the water only makes it flow again.** A looping Agent is given a low maximum tool-call count; after session compaction it repeats the task, hits the ceiling and must summarize unfinished work. Ask what keeps generating the unnecessary calls—stale state, misunderstood feedback, blind retry, missing completion test—then change one source of that behavior rather than treating the cap as the repair. Keep a real Host budget/safety fuse; if it trips, record the task as unfinished with a minimal recoverable next step, not falsely completed. Compare later task completion, retries and total spend.
34. **An Agent learns to “give itself acupuncture” (像中医一样给自己针灸).** A tool loop is slow but the fault is invisible from its final answer. Place a few **targeted, temporary probes** along the observable execution pathway—for instance request/goal → model or tool routing → tool input/output → progress check → next action—and locate the first divergence or repetition. Try the smallest reversible intervention at that junction, then check the complete real task again. Use permitted redacted traces, not imagined access to hidden thoughts or indiscriminate collection; remove probes when their diagnostic value ends.

35. **An Agent changes its own startup or communication path, restarts, and disappears.** Before the first live write, preserve the known-good state and arm a 5–10 minute rollback timer owned by the Host—not by the Agent process. Confirm that the timer is actually active before applying the change. After restart, cancel it only when a human or reachable peer Agent has completed a normal two-way exchange with the changed Agent through a path that the change did not break; the Agent's own “I'm healthy” message is not independent confirmation. If no confirmation arrives, the external executor restores only this change, restarts the Agent and records whether recovery worked, without an LLM or human in the timeout path. Serialize apply/confirm/rollback, make the executor idempotent, and ensure an old timer cannot undo a later change. A session/coding Agent should use durable Git/worktree recovery rather than inventing a daemon. See [the resident-runtime wiring example](examples/change/RESIDENT-TIMED-ROLLBACK.md).

36. **A task looks unusually expensive, but nobody knows where the resources went.** For a representative task or recurring anomaly, use `tools/resource_ledger.py record` to capture task class, route, outcome, verification, available usage with its source, and a durable evidence reference; use `review` to compare similar samples. Leave unavailable metrics unknown. Do not log every turn, prompts or private reasoning. The ledger surfaces patterns; it does not decide waste or prove causation.

37. **A lower-token run is celebrated even though the result is worse.** Compare similar tasks on verified completion, correctness, rework, retries, elapsed time and total cost. Reject a saving that shifts work into missed requirements or later repair. Spend more when the task genuinely needs more reasoning, verification or a capable route; fewer tokens alone is not success.

38. **A task approaches its resource budget before it is complete.** Treat a budget as an authorized boundary or safety fuse, not as a reason to pretend the work is finished. Reassess the value and risk of the next action, choose the least-cost adequate route, and use a more capable route when evidence shows it is needed and authorized. If a hard fuse stops execution, preserve the partial result and a recoverable next step; report the task as unfinished.

39. **Every Agent is busy, but verified work is not flowing.** Look for the current system bottleneck and protect its capacity; reduce avoidable work-in-progress, handoff queues and parallel work that only piles up unfinished results. Do not maximize each Agent's utilization as a goal. Measure throughput by useful, verified task completion.

40. **Agents become reluctant to report cost or use a necessary capability because high spend is treated as failure.** Replace punitive per-Agent token quotas and leaderboards with transparent task-level evidence, clear authority/budget boundaries and constructive review of the workflow. Distinguish avoidable waste from justified investment; make it safe to report uncertainty, mistakes and resource needs. Preserve autonomy while holding outcomes accountable.

## Build the next brick

A brick may inspire an opposite, a combination, a tool, a test, a question for another Agent, or a candidate the original example never anticipated. New bricks may originate from the Agent's own observations, not just from human prompts or this list. The list is deliberately incomplete.

When a naturally occurring task exposes a useful new move, remember the **concrete situation and its observed result** where they will genuinely help future work. Do not accumulate a second handbook or force every experience into this file. If a brick stops earning its cost, change or remove it.
